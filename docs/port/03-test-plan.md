## Scope

This plan changes coordinate handling, adb device binding, and text input in a
Python ADB-automation bot. There is no web UI. "Pages/routes" below map to
in-game screens reached over adb.

## Offline unit tests (no emulator, no adb, no game)

Every path this plan changes is a pure function or a mockable subprocess call.

- `core/coord_utils.py` — round-trip `pixel_to_percent` → `percent_to_pixel`
  returns the original within rounding. Boundaries: 0, 100, and the base
  dimensions 1080 / 2460.
- `cmd_program/screen_action.py::_convert_if_percentage` — int passes through
  unchanged; float 0–100 converts as a percentage of the base; float > 100
  casts to int rather than being read as a percentage.
- `core/ocr.py::_normalize_frame_resolution` — **the key assertion.** A frame
  already at base height must be returned WITHOUT a resize (identity, not a
  copy). A frame at any other height must come back at base height. This is the
  test that makes the 2456/2460 drift impossible to reintroduce silently.
- `cmd_program/screen_action.py` device resolver — mock `subprocess.run`:
  no devices → returns None and re-probes on the next call; device present →
  cached; device disappears mid-run → re-probes rather than reusing a stale id.
- `cmd_program/screen_action.py::input_text` — mock `run_adb_command`:
  must not raise TypeError, and must target the resolved device rather than
  any hardcoded serial.

Note: the existing `test_coords.py` has NO assertions — it prints success
unconditionally. Replace it; do not treat it as coverage.

## In-game screens to verify (requires emulator)

- **Home screen** — `references/TextArea/Home.json` fields (`Home.Power`,
  `Home.Gems`, `Home.Coal`) OCR to the values visibly on screen. This is the
  real proof that the coordinate fix landed, because these ROIs are percentage
  boxes resolved against the normalised frame.
- **Mail** — `collect_mail_rewards`. Simple and idempotent; the first
  end-to-end run.
- **Gathering** — the only live caller of `input_text` (`usecases/gather.py:112`
  calls `input_text("8")`). Must be verified separately because the mail task
  does not touch that code path at all.

## Key interactions to verify

- Startup ordering: OCR server started BEFORE `adb connect` must either fail
  loudly or self-recover — it must not silently bind a null device.
- Resolution gate: `run.sh` must hard-fail when `adb shell wm size` is not
  1080x2460, before either process launches.
- Navigation recovery: `core/recalibrate.py` returns the app to Home from a
  nested screen (taps `Global.Back` / `Global.Close` in a batch loop).

## Edge cases

- adb drops mid-run (MuMu sleeps) → next tap re-probes instead of using a
  stale device id.
- Emulator display set to anything other than 1080x2460 → hard fail at launch,
  not mis-taps.
- OCR server dies while `Main/main.py` is running → main gets connection errors
  to localhost:8000; confirm whether that surfaces or hangs.
- Long run memory: RSS of the OCR process over a full daily loop (the built-in
  RAM guard is inert on macOS — see the eng review).

## Critical paths

1. `run.sh` → adb connect → wm size assert → OCR server up → mail collected
   end to end, with `db/players/<id>.json` `last_visit` updated.
2. Gathering task completes without a TypeError from `input_text`.
3. Home-screen OCR values match what is on screen (coordinate correctness).
